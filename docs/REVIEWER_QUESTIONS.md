# Reviewer questions with code-based answers

These are preparation prompts, not a script for claiming features beyond the evidence. Open the named module/test when explaining an answer.

| Question                                                    | Answer and evidence                                                                                                                                                                                                                          |
| ----------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| What problem does Brightloop solve?                         | It joins catalog, quotations, subscription state, recurring invoices, external payment records and reporting in one persistent local workspace. Follow PROJECT_FLOW.md.                                                                      |
| Why SQLite rather than a hosted backend?                    | The chosen requirement is local-first operator-controlled storage. A persistent Node service uses node:sqlite, WAL and foreign keys. This trades easy serverless scaling for simple local ownership and backup. See db.ts and migrations.ts. |
| Why not store records in browser localStorage?              | Browser storage cannot enforce shared authorization or durable server-side accounting. Business records live in relational SQLite tables; the browser has an HTTP-only session cookie.                                                       |
| How do you store passwords?                                 | Salted scrypt, a memory-hard password derivation algorithm. Each password has a random salt. There is no plaintext password column. authentication.ts and security.test.ts.                                                                  |
| How is email verification different from login?             | Signup creates an unverified account and hashed expiring token. A single-use verification confirms the address; login then validates password and creates a separate opaque session. test:auth proves the full path.                         |
| What happens if verification is resent?                     | The user/purpose token is atomically replaced. The previous link fails; requests are rate-limited. security-tokens.ts and the authentication browser suite.                                                                                  |
| What stops reset-link theft from becoming permanent access? | Tokens are short-lived and single-use, stored hashed. Reset revokes all sessions. The link itself is still a bearer secret and must be protected in transit/logs.                                                                            |
| Can public registration create an admin?                    | No. Public signup fixes role to Customer. Admin setup is one-time and checks existing Admin inside a transaction. Only an authenticated admin invites staff.                                                                                 |
| Why use user IDs instead of matching customer email?        | Emails change and can be reused. Ownership checks join customerId to an immutable users.id. A new email address never grants another user's records.                                                                                         |
| Are hidden buttons sufficient authorization?                | No. Every mutation/route checks session and role/ownership. The browser test replays a real admin billing action as staff and verifies no run is created.                                                                                    |
| How do variants affect pricing?                             | Select one explicitly authored combination. Product base plus variant adjustment is multiplied by quantity; the plan fee is one separate line per period. quotation.ts and catalog.test.ts.                                                  |
| Why copy template lines?                                    | Existing quotations must not change when the reusable template changes. The test edits the template and verifies the prior draft remains unchanged.                                                                                          |
| What prevents an expired quote from being confirmed?        | lifecycle.ts requires a renewed validity date at confirmation; the server rejects expired transitions.                                                                                                                                       |
| What prevents double billing?                               | An immediate transaction rechecks due state, and SQLite uniquely constrains subscription plus period. Invoice, dates and discount usage commit together. concurrency.test.ts uses independent connections.                                   |
| How do missed periods work?                                 | The service loops through chronological due periods until current or the catch-up cap. Failures retain a run item; capped work gets an explicit continuation reason.                                                                         |
| What happens on January 31 or February 29?                  | The stable anchor is separate from the current date. Short months clamp, subsequent periods recover the intended day. billing.test.ts and operations.test.ts.                                                                                |
| How do pause and resume affect charges?                     | Paused records do not bill. Resume picks the next anchored date on/after today and skips paused time. There is no implied proration.                                                                                                         |
| How are discounts chosen?                                   | Active eligible rules sort by priority then ID; only one wins. Product-specific quantity/purchase minimums use eligible lines. Usage is consumed in the invoice transaction.                                                                 |
| Is tax calculated before or after discount?                 | After the allocated discount. Each tax rule rounds to paise per line, and its name/rate/amount is stored on invoice-line tax rows.                                                                                                           |
| Can catalog edits rewrite historical invoices?              | No. Billing saves independent snapshots. Tests change product prices and verify invoice totals stay fixed.                                                                                                                                   |
| How do partial payments and overpayment work?               | The transaction re-reads confirmed status and remaining balance. Positive amounts up to outstanding are accepted; full settlement changes status to Paid.                                                                                    |
| How do you correct money history?                           | A reversal preserves the original payment, records reason/time, reduces paid balance and adds an audit event. It does not silently edit the old amount.                                                                                      |
| Does this app actually collect money?                       | No. It records money collected externally. There is no gateway or card-charge API.                                                                                                                                                           |
| Is SMTP acceptance the same as delivery?                    | No. It means the provider accepted the message. Inbox/spam/bounce behavior needs real provider testing and is not inferred from local tests.                                                                                                 |
| Can reminders be exactly once?                              | Database event keys prevent repeated scheduling, but a crash after SMTP acceptance creates uncertainty. Reconcile before retrying; external SMTP cannot provide a distributed atomic commit with SQLite.                                     |
| Are collections, invoicing and revenue the same?            | No. The dashboard separates collected payments, confirmed invoice amounts and outstanding. MRR/ARR are explained contract estimates, not recognized accounting revenue.                                                                      |
| How do backups avoid corruption?                            | SQLite's consistent backup API rather than raw copying a live WAL database. Restore targets a new path and verifies integrity; overwrite is refused.                                                                                         |
| What supports the performance claim?                        | Reproducible 10k-record local HTTP measurements with hardware, warm-up, samples and exclusions documented. Do not extrapolate them to every deployment.                                                                                      |
| What are the main tradeoffs?                                | Single-server persistent storage; synchronous database access; explicit variant combinations; no payment processing; SMTP delivery uncertainty; environment-based scheduling settings.                                                       |
| How would you extend it?                                    | Add migrations and typed services for new records, permission checks, invariant tests and UI integration tests. Preserve invoice snapshots and existing data.                                                                                |
| What remains before public launch?                          | Real SMTP setup/test, operator-approved identity/legal/retention details, HTTPS deployment configuration, access/log controls and operator backup drills. No fabricated launch readiness.                                                    |

## Questions to ask the project team

1. Who owns SMTP, backups and production operation after the demonstration?
2. What are the real operator name, support email, jurisdiction and retention obligations?
3. Which staff should receive billing permission, and who reviews payment reversals?
4. Should future contracts support proration, stacked discounts or multiple currencies? Those are separate policy decisions.
5. What did each teammate actually implement, and which commits demonstrate it?
6. Has the landing page been supplied and tested against the preserved route contract?
